# 디테일 디자인 — 챔버 이상 검사 시스템

| 항목 | 내용 |
|---|---|
| 문서 | 디테일 디자인 |
| 대상 | 챔버 이상 검사 시스템 (ChamberInspect) |
| 구성 | FastAPI(로컬 서버) + 브라우저 화면 + onnxruntime 추론 |
| 배포 | PyInstaller onedir · Windows 7 SP1 64bit |
| 작성일 | 2026-08-25 |

## 1. 설명

### 1-1. 전체 구조

이 시스템은 **제어기 한 대 안에서 완결**된다. 로컬 서버가 뜨고 브라우저가 그 서버에
접속하는 형태다. 외부와 통신하지 않는다.

```
 ┌──────────────────── 제어기 (Windows 7) ─────────────────────┐
 │                                                             │
 │   ChamberInspect.exe                                        │
 │   ├─ launcher   앱 기동 · 파일 로거 · 브라우저 실행         │
 │   ├─ server     FastAPI (127.0.0.1:8000)                    │
 │   │   ├─ Engine       모델 1회 로드 · 추론                  │
 │   │   ├─ AutoPilot    폴더 감시 · 자동 검사 (백그라운드)    │
 │   │   └─ REST API     화면이 호출                           │
 │   └─ static     화면(HTML/CSS/JS) · 글꼴                    │
 │                          ▲                                  │
 │                          │ http://127.0.0.1:8000            │
 │                    [ 브라우저 ]                             │
 │                                                             │
 │   데이터 폴더 (앱 밖으로 이동 가능)                         │
 │   ├─ history.jsonl        검사 이력(append-only)            │
 │   ├─ file_meta.json       파일별 챔버·유형·LOT·종료시각     │
 │   ├─ app_config.json      화면 설정                         │
 │   ├─ 보관\               웨이퍼 상세(그래프용)              │
 │   └─ 로그\app_날짜.log   실행 기록                          │
 │                                                             │
 └─────────────────────────────────────────────────────────────┘
            ▲
            │ 원본 .log (읽기 전용)
      [설비 로그 폴더 / 네트워크 공유]
```

**왜 브라우저인가** — 제어기에 별도 GUI 런타임을 얹지 않기 위해서다. 화면은 HTML 로
두고 브라우저에 맡기면, 배포물은 서버와 정적 파일뿐이라 가볍고 교체가 쉽다.

**왜 로컬 서버인가** — 추론과 파일 접근은 파이썬 쪽에서 하고, 화면은 그 결과만 받는다.
서버는 127.0.0.1 에만 바인딩되어 외부에서 접근할 수 없다.

### 1-2. 점수 산출 흐름

```
  원본 .log
     │  ① 태깅   챔버(C2) · 유형(J2) · LOT(I2) · 종료시각(A·B열)
     │  ② 정렬   모델이 기대하는 센서/IO 열 순서로 맞춤
     ▼
  [모델] 과거 센서 + IO  ──►  미래 센서 예측
     │
     │  ③ 복원오차 = |실제 − 예측|  (시점 × 센서)
     │  ④ 누적     = 시간축으로 합산
     ▼
  원점수  ──  ÷ (유형 임계 × 유형 배율)  ──►  이상 점수 (1 = 판정선)
                                               │
                                               ├─ < 1     양품
                                               ├─ 1 ~ 2   주의
                                               ├─ 2 ~ 3   경고
                                               └─ ≥ 3     심각
```

**정규화를 두는 이유** — 유형마다 원점수의 크기가 다르다. 임계로 나눠 1을 판정선으로
맞추면 유형이 섞여 있어도 같은 축에서 비교·평균할 수 있다.

### 1-3. 모델 상세 — 구조와 산출물 계약

**구조 — 왜 '예측' 모델인가**

```
      과거 구간의 센서값 (w 스텝)  ┐
                                   ├─►  [TCN]  ─►  미래 구간의 센서 예측 (h 스텝)
      IO 상태 (밸브 개폐)          ┘                    │
                                                        ▼
                                        복원오차 = |실제 − 예측|  (시점 × 센서)
```

- 정상 데이터만으로 학습한다. 정상에서는 "과거+IO 를 보면 미래가 맞는다" 가 성립하고,
  이상에서는 예측이 빗나간다 — 그 빗나간 정도가 점수다. **불량 표본이 없어도 성립**한다.
- IO 가 입력에 있으므로 밸브를 열어 생기는 정상적 급변은 예측에 이미 반영된다.
  센서만 보는 모델이 내는 '밸브 오탐'이 구조적으로 제거된다.
- 오차가 시점×센서 단위로 나오므로, 웨이퍼 점수의 부산물로 **원인 센서·문제 구간**이
  함께 나온다. 화면의 센서별 점수·누적 음영이 이것이다.

**산출물 계약 (학습 앱 → 이 시스템)**

모델 폴더에 세 파일이 한 벌이다. 이 계약이 학습 앱과 검사 앱의 경계다.

| 파일 | 내용 | 이 시스템이 쓰는 곳 |
|---|---|---|
| `tcn_forecast.onnx` | 예측 모델 본체 | Engine 이 onnxruntime 으로 1회 로드 |
| `recon_meta.npz` | 센서/IO 열 이름 · 표준화 평균/편차 · 잔차 허용한계(`resid_abs_limit`) · 창 크기(w/h/stride) · 스키마 모드 | 열 정렬(모델 순서로) · 센서별 0~2 점수의 '정상 상한' · 창 구성 |
| `search_best.json` | 학습 탐색 결과 — 전역 임계 + **유형별 임계**(`threshold_by_recipe`) · 점수 정규화 방식 식별 정보 | 판정선(임계=1 정규화의 분모) · `score_norm` 자동 감지 |

**Engine 의 로드 규칙**

```
앱 시작(또는 모델 교체) 시 1회:
  ① .onnx + recon_meta.npz 로드  — 없으면 검사 불가로 명시
  ② search_best.json 에서 임계 탐색
       유형별 dict 발견  → threshold_mode = per_recipe
       전역값만          → threshold_mode = global
       아무것도 없음     → threshold_mode = none  ★판정 보류(임의값 생성 금지)
  ③ score_norm 감지 (none | time | final)
       time/final(모델이 이미 스텝 평균) → 앱의 타임포인트 정규화 자동 무시
                                            (이중 정규화 방지)
검사 중에는 다시 로드하지 않는다 — 대량 처리에서 로드 비용이 지배하지 않도록.
```

**판정 구간** — 공정 첫 스텝은 이전 공정 잔류(carryover)로 정상인데도 오차가 크다.
첫/끝 스텝은 판정에서 제외하며, 화면의 음영·설명도 같은 구간 정의를 따른다.

**배점 모드 (선택)** — 밸브 조건별 가중 점수 `S(w) = Σ w·max(0, 초과분)`.
분포가 원점수와 달라 모델 임계를 그대로 쓸 수 없으므로, 전용 임계 θ(w) 를
OK 재추론(3σ) 또는 분위수 매칭(오탐률 보존)으로 재보정해서 쓴다.

### 1-4. LOT 단위 산포

개별 판정은 "이 한 장이 넘었는가"만 본다. 아직 아무도 넘지 않았지만 **점점 나빠지는
중**인 상태는 잡히지 않는다. 그 구간을 보기 위한 지표다.

```
  같은 LOT 의 웨이퍼 묶음
     │
     ▼
  초과 강도 = 평균( max(0, 이상점수 − 1) )
            = 넘은 비율 × 넘은 폭 평균

     0.00  아무도 안 넘음
     0.05  25장 중 5장이 평균 1.25배 → (5/25) × 0.25
     0.80  대부분이 크게 넘음
```

넘은 **장수**가 늘어도, 넘은 **폭**이 커져도 값이 오른다. 두 방향을 한 값에 담기 위한
형태다(상방 부분적률 계열).

### 1-5. 설계 원칙

이번 개정에서 반복적으로 적용한 판단 기준이다.

| 원칙 | 적용 예 |
|---|---|
| 실패를 삼키지 않는다 | 저장 실패를 콘솔·응답·화면에 노출, 완료 문구보다 앞세움 |
| 없는 값을 0으로 보이지 않게 한다 | 데이터 없는 기간은 빈칸, 임계 없으면 판정 보류 |
| 필수 입력은 지원 범위가 넓은 수단으로 | 날짜는 필수·시간은 선택 |
| 오래 걸리는 일은 중간을 보여 준다 | 진행률·처리율·예상시간·중간 저장 |
| 되돌릴 수 있게 둔다 | 표시 규칙만 바꾸고 원점수 보존, 콘솔은 옵션으로 |
| 설정이 바뀌면 파생값도 다시 만든다 | 읽은 칸 기록 → 칸 변경 시 자동 재추출 |
| 외부에 의존하지 않는다 | 글꼴까지 내장, 외부 참조 0건 |

**설계 의도**

- `Engine` 은 모델을 **1회만** 올린다. 검사마다 로드하면 대량 처리에서 그 비용이 지배한다.
- `AutoPilot` 은 스레드 1개로 감시·검사·정리를 모두 맡는다. 스레드를 늘리면 제어기 자원을
  설비 제어와 다투게 된다.
- 표시 규칙은 **한 곳(`_display_rule`)** 에서만 나온다. 임계·배수를 바꾸면 산점도·목록·
  불량률 추이·1시간 현황이 동시에 바뀌어야 하기 때문이다.
- `file_meta.json` 의 `lot_c`(읽은 칸)가 재추출 판단의 근거다.

### 2-7. 데이터 형식

**원본 로그 (탭 구분)**

```
행1 : 헤더
행2 :  A      B      C          …    I           J
       날짜   시간   PMCUNIT11  …    7c218394…   29aece39…
                     └챔버           └LOT        └유형
행3~: 데이터 (A=날짜, B=시간, 이후 센서·IO 값)
마지막 행의 A·B → 공정 종료 시각
```

**모델 산출물 (모델 폴더 — 읽기 전용)**

```
모델폴더\
  tcn_forecast.onnx      예측 모델 (윈7 은 IR≤8 — 5.모델 변환으로 하향)
  recon_meta.npz         열 이름·표준화·잔차 한계·창 크기 (onnx 와 반드시 한 쌍)
  search_best.json       전역·유형별 임계 + 점수 정규화 방식
```

메타가 빠지면 로드 자체를 거부하고 사유를 표시한다(짝이 안 맞는 모델로 잘못된
점수를 내는 것보다 멈추는 쪽이 낫다).

**file_meta.json**

```json
{
  "WUK370A_w0001": {
    "chamber": "dsv5",
    "lot":     "7c218394aa11",
    "lot_c":   "R2C9",
    "lot_v":   1,
    "end_ts":  "2026-08-01T09:02:00",
    "ets_v":   2
  }
}
```

`lot_c` 는 **어느 칸으로 읽었는지**를 남긴 값이다. 설정된 칸과 다르면 그 파일은 다시
읽어 덮어쓴다. 이 값이 없으면 칸을 바꿔도 전부 건너뛰어 틀린 값이 그대로 남는다.

**history.jsonl** (한 줄 = 웨이퍼 1장, append-only)

```json
{"ts":"2026-08-01T09:02:00","date":"2026-08-01","wafer_id":"WUK370A_w0001",
 "score":1.42,"verdict":"NG","threshold":1.0,"n_flag_sensor":3,
 "recipe":"29aece39…","chamber":"dsv5",
 "score_raw":3.81,"score_w_raw":null,"n_bad_lines":0,"n_tp":1024,
 "model":"…"}
```

- **원점수(`score_raw`)를 함께 남긴다.** 나중에 임계·배수를 바꿔도 **표시만 다시 계산**
  하면 되고 원본은 보존된다.
- `model` 로 어느 모델이 낸 결과인지 구분한다. 모델을 바꾸면 이력이 섞이지 않는다.
- **LOT 은 여기 저장하지 않는다.** 파일별 메타(`file_meta.json`)에서 웨이퍼 이름으로
  찾는다. 이력을 건드리지 않고 LOT 만 나중에 보강할 수 있는 이유가 이것이다
  (검사 결과를 다시 쓰지 않으므로 판정이 바뀔 여지가 없다).
