# 기능별 CPU 사용량 정리 — 무엇을 덜어낼지 정하기 위한 자료

측정 환경: 실제 데이터 규모(웨이퍼 1장 = 타임포인트 1500 × 센서 12 + IO 81, 파일 2.6MB),
torch 백엔드 CPU 추론, **4스레드 기준**. 목록 집계는 8만 장 기준.
작성 기준일: 2026-08-20

---

## 한눈에 보기

| 순위 | 기능 | 비용 | 근거 |
| --- | --- | --- | --- |
| **1** | **RCA (원인 분석)** | **1회 = 검사 수백 장분** | 후보마다 모델 재추론 (측정 못 함, 구조상 추정) |
| **2** | **리포트 생성 (PNG)** | **308 ms/장** | 실측 — matplotlib 렌더 |
| **3** | **웨이퍼 검사 (추론)** | **10.6 ms/장** | 실측 — 슬라이딩 윈도우 189개 순전파 |
| 4 | 파일 파싱 | 10.0 ms/장 (캐시 시 1.9) | 실측 |
| 5 | 보관 저장 (npz 압축) | 3.6 ms/장 | 실측 |
| 6 | 목록·집계 재계산 | 8만 장에 ~50 ms | 실측 |
| 7 | 화면 그리기 (브라우저) | 서버 CPU 0 | 클라이언트 부담 |
| 8 | 설정·조회류 전부 | 무시 가능 | 파일 읽기 수준 |

**핵심**: 정상 운영 중 CPU를 쓰는 것은 사실상 **검사(추론+파싱+보관) = 약 24 ms/장** 뿐입니다.
**리포트와 RCA는 사용자가 버튼을 누를 때만** 도는데, 한 번에 검사 수백~수천 장분을 먹습니다.
덜어낼 대상을 찾는다면 여기가 유일하게 의미 있는 지점입니다.

---

## 1. 사용자가 실행하는 무거운 작업

### 1위 — RCA (원인 분석) 🔴 압도적 1위

| 항목 | 내용 |
| --- | --- |
| 트리거 | NG 웨이퍼 상세 > [RCA 생성] 버튼 |
| 비용 | **측정 불가 — 구조상 검사 1장의 수백 배 이상** |
| 왜 | 조정 후보(delta 13단계) × 제어 대상 × 조정 스텝 조합마다 **모델을 처음부터 다시 돌림**. 상위 후보끼리의 **조합**은 13^2 = 169가지를 추가로 계산 |
| 병렬화 | 없음 (순차) |
| 캐시 | 결과만 저장 — 같은 웨이퍼 재클릭은 즉시 |

**덜어낼 여지가 가장 큽니다.**
- delta 그리드를 13단계 → 5단계로 줄이면 약 2.6배 감소
- 조합 탐색(`combo_top_n`)을 끄면 169회 계산이 사라짐
- 둘 다 적용하면 **10배 이상 감소**하며, 권고값의 해상도만 거칠어집니다

### 2위 — 리포트 생성 🟠

| 항목 | 내용 |
| --- | --- |
| 트리거 | [선택 리포트] / [전체 리포트] 버튼 |
| 비용 | **308 ms/장** (12센서 격자 PNG 1장 기준, 실측) |
| 왜 | matplotlib 렌더링. 검사 자체(10.6 ms)의 **약 30배** |
| 병렬화 | 프로세스 풀 (코어 수만큼) — CPU를 전부 먹을 수 있음 |
| 참고 | 100장 리포트 = 약 30초분의 CPU 점유 |

**덜어낼 여지**: DPI 하향, 센서 격자 축소, 또는 PNG 대신 브라우저 렌더(HTML)로 전환.
현재도 `_cpu_workers()`로 워커 수가 제한되며 **설정 > CPU 사용 제한**을 따릅니다.

## 2. 상시 도는 작업 (자동 감시 · 검사)

웨이퍼 1장을 처리하는 전체 비용 = **약 24 ms** (4스레드 기준)

| 단계 | 비용 | 비고 |
| --- | --- | --- |
| 파일 파싱 | 10.0 ms | 2회차부터 캐시로 **1.9 ms** |
| **모델 추론** | **10.6 ms** | 슬라이딩 윈도우 189개를 한 배치로 |
| 복원오차·점수 계산 | 1 ms 미만 | numpy 벡터 연산 |
| 보관 저장 (npz 압축) | 3.6 ms | 91KB/장 |

**스레드 수에 따른 추론 시간** (같은 작업):

| 스레드 | 시간 | 비고 |
| --- | --- | --- |
| 1 | 37.7 ms | |
| 2 | 21.1 ms | |
| **4** | **10.6 ms** | 기준 |
| 8 | 13.6 ms | **더 느려짐** — 스레드 관리 비용이 이득을 넘음 |

> **중요**: 코어를 더 준다고 빨라지지 않습니다. 이 모델 크기(24.6만 파라미터)에서는
> **4스레드가 최적**입니다. 설정 > CPU 사용 제한에서 코어를 넉넉히 비워 두어도
> 검사 속도는 거의 그대로입니다.

**처리량 환산** (4스레드, 파싱 캐시 없음 기준):
- 1장 24 ms → **초당 약 40장 / 시간당 약 15만 장**
- 실제 운용 시 병목은 CPU가 아니라 **디스크 읽기**일 가능성이 높습니다

## 3. 화면·조회 기능 (거의 무시 가능)

| 기능 | 서버 CPU | 비고 |
| --- | --- | --- |
| 산점도 표시 | 8만 장에 ~50 ms | JSON 직렬화 11MB — CPU보다 **브라우저 메모리**가 문제 |
| 판정 재계산 (임계·밴드 변경) | 8만 장에 ~2 ms | 캐시됨 |
| 챔버별 불량률 추이 | ~50 ms | 산점도와 같은 집계 재사용 |
| 산포 추세 | ~100 ms | 그룹화 + 중앙값/MAD |
| 최근 1시간 현황 | 무시 가능 | 같은 집계 재사용 |
| 웨이퍼 상세 열기 | 0.3 ms | 보관 npz 로드 |
| 센서별 그래프 | 무시 가능 | 서버는 데이터만, 그리기는 브라우저 |
| HTML 내보내기 | 수백 ms | 데이터 양에 비례 |
| n_tp 백필 | 0.1 ms/장 | step 배열만 읽음 |

**산점도는 CPU 문제가 아닙니다.** 8만 장이면 JSON 11MB + DOM 노드 수십만 개로
**브라우저가 느려집니다.** 서버 CPU를 아껴도 개선되지 않습니다.

## 6. 덜어낸다면 — 우선순위 제안

효과가 큰 순서입니다.

| 순위 | 대상 | 절감 | 잃는 것 |
| --- | --- | --- | --- |
| 1 | **RCA 조합 탐색 끄기** | 169회 재추론 제거 | 두 제어 변수를 동시에 조정하는 권고가 사라짐 |
| 2 | **RCA delta 그리드 13 → 5단계** | 약 2.6배 | 권고 조정폭이 거칠어짐 |
| 3 | **리포트 DPI·센서 격자 축소** | 2~3배 | 그림이 작아짐 |
| 4 | 리포트를 PNG → HTML 로 | 렌더 비용 거의 0 | 서버 렌더 결과물이 없어짐 (브라우저 필요) |
| 5 | 파싱 캐시 항상 사용 | 8 ms/장 | 디스크 사용량 증가 (489KB/장) |
| 6 | 보관 압축 끄기 | 3.6 → 1 ms/장 | 저장 용량 약 3배 |

**권장**: 1·2번만 적용해도 실질적인 CPU 부담은 대부분 사라집니다.
검사 경로(3~5위)는 이미 충분히 가벼워서 손대도 체감이 없고, 오히려
캐시·압축을 끄면 디스크가 병목이 됩니다.

## 부록 — 측정 방법

- 모델 추론: 실제 `.pt` 모델의 네트워크에 실제 규모 입력 `(189, 158, 16)`을 넣어 5회 평균
- 파싱: 1500행 × 93열 탭 구분 파일(2.6MB)을 `pandas.read_csv` 10회 평균
- 리포트: 4×3 격자에 1500포인트 2계열씩, `dpi=100` PNG 저장 3회 평균
- 보관: 실제 보관 파일과 같은 구조(float16 3종 + step)로 10회 평균
- 집계: 8만 행 dict 리스트 직렬화·필터 1회

측정하지 못한 것: **RCA 실행 시간**(실데이터와 H 모델이 필요). 코드 구조상
후보 수만큼 모델을 재실행하므로 다른 기능과 자릿수가 다르다는 점만 확인했습니다.
