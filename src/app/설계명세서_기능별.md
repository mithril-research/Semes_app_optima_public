# 웨이퍼 품질 검사 시스템 — 기능별 설계 명세서

- 대상: FastAPI 백엔드(server.py) + WebView2 네이티브 창 + onnxruntime 추론
- 각 기능마다 [1.요구사항 명세서 · 2.본 설계 · 3.디테일 디자인 · 4.테스트 케이스] 를 기술한다.
- 테스트 케이스는 기능별로 네거티브 50% 이상을 포함한다.
- 작성 기준일: 2026-07-21

## 기능 목록
- F1. 웨이퍼 이상탐지 검사
- F2. 이상점수 정규화(임계=1 기준)
- F3. 검사 모델 관리 + 기본 모델 지정
- F4. 리포트 생성(모델별 분리 + 렌더 직렬화)
- F5. 추세/산점 분석
- F6. 상세 진단(그림/센서)
- F7. 이력 검색(아카이브 + 월 달력)
- F8. 챔버 현황(dsv1~6)
- F9. 레시피별 임계 배수 + 이력/보관 관리(설정)
- F10. 자동 감시/백업(AutoPilot)
- F11. 배포/설치(WebView2 + 전제조건 패치 + 롤백)

# F1. 웨이퍼 이상탐지 검사

## 1. 요구사항 명세서
- **역할/목적**: 선택된 모델로 폴더의 웨이퍼 CSV 를 검사하여 웨이퍼별 이상점수·판정(OK/NG)·이탈센서수를 산출한다.
- **설계 범위(블랙박스)**: 모델 추론 내부(masked-future TCN, onnx), CSV 파싱 세부.
- **동작 시나리오**
  - 선행조건: 유효 모델 1개 로드, 검사 폴더에 CSV 존재.
  - 후행조건: `STATE["results"]`·`STATE["recs"]` 갱신, 요약(전체/불량/커버리지) 산출, 이력 append.
  - 기본: 폴더 선택 → 검사 → 웨이퍼별 점수/판정 표 + 요약 표시.
- **제약사항**: ProcessStep 0 제외(SKIP_STEPS). 점수=Σ max(0, |actual-expected|/OK_limit). 센서 커버리지 낮으면 경고.

## 2. 본 설계
- **현상 기록**: 설비별 센서 구성이 달라 커버리지 낮으면 점수 왜곡.
- **개선 요청**: 커버리지 표기, 모델별 이력 분리, 점수 정규화(F2).
- **변경 범위**: `Engine.load/select`, `_summary`, `_append_history`, `/api/inspect`, `/api/results`.
- **제약 정의**: 결과는 메모리 캐시(STATE) — 상세/그림 endpoint 가 재추론 없이 재사용.

| 변경 전 | 변경 후 |
|---|---|
| 커버리지 표기 없음 | 센서 일치율(coverage) 경고 |
| 이력 모델 혼재 | 모델 태그(_model_id) 부착 |

## 3. 디테일 디자인
검사는 `/api/inspect` → 폴더 CSV 로드 → `ENGINE.model` 추론 → 웨이퍼별 record/점수 → STATE 캐시 + `_append_history`. `_summary` 가 전체/불량/커버리지 집계.
```
UI --POST /api/inspect(folder)--> server
      로드→추론→STATE.results/recs, _append_history(model tag)
   <-- {results, summary, coverage, inspected_at}
```

# F2. 이상점수 정규화(임계=1 기준)

## 1. 요구사항 명세서
- **역할/목적**: 서로 다른 모델·레시피의 점수를 한 화면에서 비교 가능하도록 임계=1 기준으로 정규화한다.
- **설계 범위(블랙박스)**: 원점수 산출 로직(F1).
- **동작 시나리오**
  - 선행조건: 웨이퍼별 원점수·레시피·임계 존재.
  - 후행조건: 표시 점수 = 원점수/base, 임계선 = 레시피 배수(mult).
  - 기본: 표/추세/산점/그림 모두 정규화 점수로 표시.
- **제약사항**: base = decision/mult, mult = 레시피 배수(29a=1.1, 그 외 1.0). 29a 는 길고 관대하여 1.1.

## 2. 본 설계
- **현상 기록**: 모델/레시피마다 점수 스케일이 달라(예 19673 vs 8.6) 그래프가 깨짐.
- **개선 요청**: 전 화면 임계=1 기준 통일.
- **변경 범위**: `_score_view`, `_plot_threshold_dict`, `_hist_ratio`, 그림 렌더의 threshold 전달.
- **제약 정의**: 옛 이력(raw)·새 이력(정규화) 혼재 시 score/threshold 로 동일 값 도출.

| 변경 전 | 변경 후 |
|---|---|
| 원점수 그대로 | 표시=raw/base, 임계선=mult |
| 레시피 무관 | 29a=1.1 배수 반영 |

## 3. 디테일 디자인
`_score_view(wid, raw)` → raw/base (base=decision/mult). 그림 임계선은 `_plot_threshold_dict()` 로 mult 전달. 이력은 `_hist_ratio=score/threshold`.

# F3. 검사 모델 관리 + 기본 모델 지정

## 1. 요구사항 명세서
- **역할/목적**: 여러 모델(내장/외장)을 목록에서 선택·전환하고, 특정 모델을 '기본 모델'로 지정해 앱 시작 시 자동 로드한다.
- **설계 범위(블랙박스)**: 모델 파일 포맷(onnx+npz/pt).
- **동작 시나리오**
  - 선행조건: 유효 모델 폴더(내장 또는 exe 옆 모델\ 등).
  - 후행조건: 선택 시 즉시 전환, '기본 설정' 시 app_config 저장 → 다음 실행 자동 로드.
  - 기본: 드롭다운 선택 → [기본모델로 설정] → 목록에 '★ (기본)' 표시.
- **제약사항**: 기본은 `default_model`(경로 또는 '__bundled__')로 저장. 삭제/무효면 자동 탐색 복귀.

## 2. 본 설계
- **현상 기록**: 재시작마다 내장 모델로 초기화 → 매번 재선택 필요.
- **개선 요청**: 특정 모델을 기본으로 고정.
- **변경 범위**: `_resolve_art`(기본 우선), `/api/model/set-default`·`/clear-default`, `/api/models`(default_dir), 프론트 버튼·표시.
- **제약 정의**: 내장 모델은 경로가 설치마다 달라 '__bundled__' 센티넬로 저장.

| 변경 전 | 변경 후 |
|---|---|
| 시작 시 자동 탐색만 | ① 저장된 기본 모델 우선 로드 |
| 기본 지정 불가 | [기본모델로 설정] 버튼 + 목록 ★표시 |

## 3. 디테일 디자인
```
[기본 지정] UI --POST /api/model/set-default{dir}--> app_config.default_model 저장
[앱 시작]   Engine.load → _resolve_art:
              ① default_model(=경로/'__bundled__') → ② IO_ARTIFACTS → ③ exe옆 모델\ → ④ 내장
[목록]      GET /api/models → default_dir 반환, 프론트가 '★ (기본)' 표시
```

# F4. 리포트 생성(모델별 분리 + 렌더 직렬화)

## 1. 요구사항 명세서
- **역할/목적**: 검사 결과를 그림(overlay/heatmap/누적 + 상위 센서)과 predictions.csv 로 저장한다. 모델별로 분리 보관.
- **설계 범위(블랙박스)**: 그림 렌더 함수 내부(recon_explain).
- **동작 시나리오**
  - 선행조건: 검사 결과 존재.
  - 후행조건: `리포트\<모델>\<wafer>\*.png` + `리포트\<모델>\predictions.csv` 생성.
  - 기본: [전체/선택/1장] 리포트 → 진행률 → 완료 시 CSV 링크.
- **제약사항**: 백그라운드 스레드 수행. matplotlib(pyplot)은 스레드 비안전 → 렌더 직렬화.

## 2. 본 설계
- **현상 기록**: ① 모델 변경 시 기존 리포트 전부 삭제. ② 리포트 중 다른 탭 가면 생성이 중간에 실패("되다마네").
- **개선 요청**: 모델별 리포트 유지, 탭 이동에도 끝까지 생성.
- **변경 범위**: `_model_slug`·`_report_root`·`_pred_csv`, `_plot_path`/`_sensor_dir`(모델 네임스페이스), `_PLOT_LOCK`, `_run_report`, `pollReport`.
- **제약 정의**: 모델 select 시 리포트 삭제 안 함. reload(웨이트 변경) 시에만 현재 모델 폴더 비움.

| 변경 전 | 변경 후 |
|---|---|
| `리포트\<wafer>\` 단일 | `리포트\<모델>\<wafer>\` 분리 |
| 모델 변경=전체 삭제 | 삭제 안 함(모델별 보존) |
| 렌더 락 없음(충돌) | `_PLOT_LOCK` 직렬화 |
| 탭 이동 시 진행 유실 | pollReport 재개(서버는 계속) |

## 3. 디테일 디자인
```
UI --POST /api/report--> thread(_run_report)  --각 웨이퍼--> ensure_plot/sensor
UI --GET /api/report(1s)--> {running,done/total}   (탭 이동해도 서버 스레드 지속)
동시 상세/이력 탭의 plot 요청 == 같은 _PLOT_LOCK 으로 직렬화 → pyplot 충돌 없음
```

# F5. 추세/산점 분석

## 1. 요구사항 명세서
- **역할/목적**: 기간별 이상점수 추세선·산점도를 현재 모델 이력 기준(임계=1)으로 표시.
- **동작 시나리오**: 선행=현재 모델 이력 1건↑ / 후행=선택 기간 그래프 / 기본=기간 선택→표시.
- **제약사항**: 모델 혼재 방지 위해 현재 모델 이력만. 웨이퍼별 최신 1건 dedup.

## 2. 본 설계
- **현상 기록**: 모델 혼재로 스케일 붕괴, 유령/중복 점, 기간 고정.
- **개선 요청**: 모델별 필터, dedup, 기간 선택, 정규화.
- **변경 범위**: `_history_for_current_model`, `_hist_ratio`, 산점 dedup, 프론트 기간 셀렉터.

| 변경 전 | 변경 후 |
|---|---|
| 전체 이력(혼재) | 현재 모델만 |
| 원점수 | score/threshold |
| 중복 점 | wafer별 최신 1건 |

## 3. 디테일 디자인
`/api/trend` → `_history_for_current_model()` → `_hist_ratio` 정규화 → 기간 필터 → 시계열/산점 데이터.

## 2. 본 설계

### 2.1 구성 및 책임

| 구성요소 | 구현 파일 | 책임 |
|---|---|---|
| 브라우저 화면 | `static/index.html` | 사용자 입력 검증, HTTP 요청, 결과 표시, 상태 폴링 |
| API 서버 | `server.py` | 요청 모델 검증, 검사 엔진 호출, 집계, 아카이브 및 설정 처리 |
| 공통 실행 관리 | `ui_runtime.py` | 코드·설치 식별, 기존 서버 확인, 캐시 제어 헤더 |
| 실행 진입점 | `launcher.py`, `desktop.py` | 브라우저/WebView2 실행 및 서버 연결 |
| 영속 저장소 | NPZ 및 JSON 파일 | 검사 원본, 앱 설정, 자동검사 설정, 파일 태그 유지 |

기본 실행은 로컬 HTTP 서버와 같은 장비의 화면을 연결한다. 검사 요청은 서버의 엔진을 호출하고 결과를 메모리 상태와 NPZ 아카이브에 반영한다. 서버 재시작 시 보관된 NPZ를 스캔해 이력 인덱스를 다시 만든다. 현재 모델 기준 이력을 화면별 조회 API가 공유한다.

```text
사용자 → 브라우저/WebView2 → HTTP API → 검사 엔진
                                  ├─ NPZ 아카이브 → 이력 인덱스 → 조회 응답
                                  └─ JSON 설정 저장 → 이후 실행 시 로드
```

### 2.2 인터페이스 공통 규칙

- GET은 조회, POST는 실행·설정 요청에 사용한다. JSON 요청 본문은 해당 Pydantic 요청 모델로 받는다. 날짜·웨이퍼 ID 등은 API별 쿼리 또는 경로 매개변수로 전달한다.
- JSON 응답 외에 그림, CSV, HTML 다운로드 인터페이스도 있다. 클라이언트는 해당 API의 콘텐츠 형식에 맞춰 처리한다.
- 오류는 API별 HTTP 상태와 오류 내용을 확인한다. 예를 들어 AutoPilot 미기동 상태는 503을 반환한다. 모든 오류가 동일한 사용자 정의 응답 구조를 갖는 것으로 가정하지 않는다.
- HTML 및 `/api/*` 응답에 `Cache-Control: no-store`, `Pragma: no-cache`, `Expires: 0` 및 서버 인스턴스 헤더를 적용한다.

### 3.2 이상분석 목록 계약

`GET /api/history/range?start=2026-09-01&end=2026-09-08`은 날짜 양끝을 포함하며, 시작·끝이 역전되면 서버에서 교환한다. 현재 모델의 이력에서 웨이퍼당 최신 한 건을 선택한다.

각 항목은 `wafer_id`, `date`, `ratio`, `ratio_thr`, `band`, `verdict`, `chamber`, `recipe`, `ts`, `end_ts`, `lot`, `lot_first`, `n_bad_lines`, `has_archive`를 제공한다. 종료 시각을 파싱해 오름차순으로 정렬하고, 종료 시각이 없으면 이력 시각을 사용한다. 두 시각 모두 파싱할 수 없으면 뒤에 배치한다.

`lot_first`는 기간을 자르기 전 현재 모델 이력에서 판정한다. 따라서 기간 필터로 첫 웨이퍼가 제외되어도 남은 웨이퍼를 임의로 첫 번째로 바꾸지 않는다. 기존 LOT 처리 구간 판정을 사용하며, 같은 LOT라도 챔버와 처리 간격에 따라 별도 구간으로 구분될 수 있다. 화면은 참인 항목에 `[LOT 첫 번째]`를 표시한다.

### 3.3 보관 기간 요청·응답

화면 표시는 `보관기간(1~60일)`이다. 입력 문자열을 숫자로 바꾸기 전에 `0000` 여부를 판별한다.

| 사용자 입력 | POST JSON | 저장되는 일수 |
|---|---|---|
| `30` | `{"days":30,"unlimited":false}` | 30 |
| `0` | `{"days":0,"unlimited":false}` | 60 |
| `0000` | `{"days":0,"unlimited":true}` | 0 = 무제한 |

저장 응답은 `days`, `unlimited`, `pruned`를 포함한다. 조회 응답은 `days`이며, 화면은 저장값 0을 `0000`으로 복원한다. 기간 설정이면 저장 직후 아카이브 정리를 수행한다. 무제한 설정에서는 해당 보관 기간을 사용하는 자동 정리를 건너뛴다.

### 3.4 서버 시작·종료 및 화면 갱신

1. 실행 진입점에서 `/api/ping-app`으로 기존 앱을 확인한다.
2. 시작 시점 코드 해시와 설치 위치가 일치하면 기존 서버에 연결한다.
3. 구버전 또는 다른 설치의 앱이 남아 있으면 최대 330초 동안 포트 해제를 기다린다. 기존 프로세스를 강제 종료하지 않는다.
4. 화면은 매번 고유 URL로 열며 API 요청에도 `cache: no-store`를 적용한다.
5. 응답의 서버 인스턴스가 바뀌거나 `pageshow.persisted`로 브라우저 캐시 복원이 감지되면 새 URL로 화면을 다시 읽는다.
6. 화면은 `alive`로 연결을 유지하고 닫힐 때 `bye`를 보낸다. 서버 종료 감시 루프가 남은 화면과 진행 작업을 고려해 종료한다.

# F13. 챔버별 모델 선택 및 배치 추론

## 1. 요구사항 명세서

설정에서 모델 묶음 폴더를 선택하면 로그 2행 C열의 PMCUNIT7~12를 DSV1~6으로 매핑하여
챔버별 ONNX 모델·메타데이터·설정·판정 임계를 적용한다. 같은 챔버의 웨이퍼들은 배치 추론한다.
기존 단일 모델 폴더 선택도 지원한다.

## 2. 본 설계

`chamber_models.py`가 DSV1~DSV6 하위 폴더를 탐색한다. `Engine`이 챔버별
모델을 로드하고 `EngineRouter`가 요청별 엔진 선택을 격리한다. 설정 화면은 적용된 DSV별
모델 경로를 표시한다. 필수 ONNX/NPZ/JSON 누락, 중복 모델, 챔버 미확인은 오류로 처리한다.

## 3. 디테일 디자인

수동·자동 검사 → C2 태그 추출 → 동일 챔버끼리 그룹화 → 각 모델의 설정으로 데이터 정렬 →
ONNX 배치 추론 → 챔버별 임계로 판정 → NPZ 저장. 상세 그래프와 재시작 후 이력에도 해당
챔버의 모델·임계를 사용한다. 모델 묶음 ID는 전체 ONNX·NPZ·JSON 내용으로 산출한다.
하위 폴더 구조, 파일 우선순위, 청크 크기, API 연결은 `docs/07_배포판_기능연결맵.md`의
「챔버별 모델 묶음」을 참조한다.
